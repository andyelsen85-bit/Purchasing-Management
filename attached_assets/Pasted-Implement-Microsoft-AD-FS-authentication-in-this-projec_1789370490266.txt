## Internal AD FS CA certificate

Some installations use an internal certificate authority.

Allow an administrator to:

- Upload a PEM certificate file
- Paste PEM certificate text
- See whether a custom certificate is configured
- Replace or remove the certificate

Validate that the supplied value contains a valid PEM certificate before saving it.

The CA certificate is public certificate material, not a private key. Do not treat it as an application secret, but do not send the complete stored PEM back to the browser unnecessarily.

Apply the configured CA dynamically to all server-side AD FS HTTPS requests, including:

- OIDC discovery
- Token exchange
- JWKS retrieval

The custom CA must extend Node.js’s normal trusted CA roots, not replace them. A custom AD FS CA must not break HTTPS requests to public services.

Do not globally disable TLS certificate validation. Never use NODE_TLS_REJECT_UNAUTHORIZED=0 or an equivalent insecure workaround.

Invalidate any relevant discovery/JWKS/HTTP-client cache when AD FS authority or CA settings change.

## Application session and login preference

After successful AD FS authentication:

- Create the project’s normal application session
- Use its existing secure cookie configuration
- Preserve existing CSRF protections
- Set a non-sensitive login preference cookie indicating that AD FS was the last login method

Use a cookie similar to:

- Name: cm_login_method or an application-specific equivalent
- Value: adfs
- Lifetime: approximately one year
- SameSite: Lax
- Secure in production
- Path: /
- It does not need to be HTTP-only if the frontend must use it to initiate automatic reauthentication

The main authenticated application session should retain its existing lifetime. If no clear lifetime exists, use 12 hours.

When the application session expires and the login preference says AD FS:

- Automatically initiate AD FS authentication once per browser tab
- Preserve the current page as the return destination
- Prevent redirect loops using sessionStorage or equivalent tab-scoped state
- Let AD FS decide whether authentication is silent based on its own SSO session
- Do not use insecure hidden-iframe authentication

On explicit logout:

- End the application session
- Clear the AD FS login preference
- Do not immediately start AD FS again
- Preserve the project’s existing logout semantics

## Deep-link preservation

Preserve direct links and email links through every login method.

Examples:

- /changes/123
- /requests/456?tab=history
- Any other protected local application route

Required behavior:

1. An unauthenticated user opens a protected local URL.
2. The application redirects to login without losing the original path, query string, or fragment.
3. AD FS, local, LDAP, or another successful login returns the user to the original route.
4. Automatic AD FS reauthentication after session expiration also returns to the current route.

For the AD FS flow:

- Include the local return target in the signed, short-lived AD FS state
- Do not trust an unsigned returnTo query parameter in the callback
- Validate the return target both before starting authentication and before redirecting after authentication
- Default to / when the value is absent or invalid

Only local application paths are allowed.

Reject:

- Absolute URLs
- Protocol-relative URLs beginning with //
- Backslashes
- javascript: or other schemes
- Control characters
- CRLF/header-injection values
- URLs pointing to another origin
- Malformed encoded values

Do not create an open redirect.

Check the frontend router carefully. Confirm whether its location hook includes query strings and whether /login?returnTo=... is still recognized as the login route without causing a redirect loop.
